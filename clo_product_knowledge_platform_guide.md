# CLO Product Knowledge Platform & AI Engineering Assistant

## Guiding architecture and implementation roadmap

This document captures the proposed direction for building an AI-powered
engineering knowledge system for the CLO Asset Management product. It is
intended to serve as a durable guiding document throughout the
initiative.

------------------------------------------------------------------------

# 1. Reframing the goal

The goal is considerably more ambitious---and more interesting---than
simply building a codebase RAG chatbot.

The initiative is to build an **AI-powered engineering knowledge system
for the CLO Asset Management product**.

A conventional RAG chatbot helps developers find relevant documents and
code. The longer-term system should be able to:

-   Understand the CLO domain and explain business concepts.
-   Understand how the existing product implements those concepts.
-   Understand the modernized architecture and its implementation.
-   Connect business requirements to legacy implementation and modern
    services.
-   Help developers make architectural and design decisions.
-   Eventually act as an engineering assistant that can inspect, write,
    and review code.

This is achievable incrementally, but some architectural decisions
should be made early so that the initial implementation does not become
a dead end.

# 2. Review of the proposed approach

The recommendations to use LlamaIndex, code-aware parsing, semantic
chunking, hybrid search, and incremental indexing are broadly sound.
There are, however, important omissions and distinctions.

## 2.1 Don't think of this as just one RAG index

There are at least four distinct sources of knowledge.

### 1. Product/domain knowledge

CLO concepts, facilities, portfolios, instruments, issuers,
transactions, compliance rules, waterfalls, IC/OC tests, and so on.

This provides **business understanding**.

### 2. Legacy implementation

Classic ASP, SQL Server stored procedures, tables, views, triggers, and
business logic.

This tells us **what the product actually does today**.

### 3. Modern implementation

.NET gRPC services, React micro-frontends, common libraries, event
propagation, database ownership, Helm charts, and so on.

This tells us **what the product is becoming**.

### 4. Architecture and engineering knowledge

Design decisions, trade-offs, ADRs, conventions, known limitations,
migration plans, and engineering guidelines.

This explains **why things are designed this way**.

These sources are related, but they should not be treated identically.

For example:

-   A stored procedure is evidence of what the legacy application
    implements.
-   An indenture is evidence of contractual requirements.
-   A domain document explains business terminology.
-   An architecture decision record explains why a particular service
    boundary was chosen.

These sources can even contradict one another.

Imagine a developer asks:

> How is a facility's principal balance calculated?

The answer might require:

1.  Understanding what principal balance means in the CLO domain.
2.  Finding the applicable contractual definition.
3.  Finding the stored procedure that implements the calculation.
4.  Finding the modern service that is replacing that logic.

Simply retrieving the five most similar text chunks will not reliably
establish that relationship.

**Recommendation:** Start with one application and one retrieval system,
but preserve the source type, provenance, and relationships between
sources from day one. There is no need for four separate databases or
four separate RAG applications.

## 2.2 Don't confuse code understanding with code parsing

Tree-sitter, Roslyn, and SQL parsers are useful, but they do not
understand business logic.

For example, a stored procedure might contain:

-   A calculation for a compliance test.
-   A calculation for a reporting field.
-   A special-case adjustment.
-   Several branches for different CLO scenarios.

An AST parser can identify the procedure, its statements, and some of
its structural relationships. It cannot reliably tell you what those
calculations mean in the CLO domain.

That understanding comes from combining:

-   Source code.
-   Comments and naming.
-   Related code.
-   Domain documentation.
-   Indenture documentation.
-   Explanations generated by an LLM, with evidence.

Distinguish two activities:

**Structural extraction:** Deterministic parsing of code and metadata.

**Semantic enrichment:** Using an LLM to explain what the extracted code
appears to do, identify concepts, and establish candidate relationships.

Keep those separate. You should be able to regenerate semantic
enrichment without having to reparse the entire repository.

## 2.3 Don't make a knowledge graph a prerequisite

Relationships are valuable, but do not start by introducing Neo4j or
another graph database.

Start by extracting relationships into ordinary structured records:

``` text
StoredProcedure: CalculateFacilityBalance
    calls:
        GetFacilityTransactions
        CalculatePrincipalAdjustment

    reads:
        Facility
        FacilityTransaction
        PurchaseLot

    called_by:
        FacilityDetails.asp
```

These can initially be stored in PostgreSQL.

Later, if graph traversal becomes important, introduce a graph database
or graph-oriented retrieval layer.

**Capture relationships early, but don't introduce graph infrastructure
prematurely.**

## 2.4 Don't assume vector search is the answer to every question

Different developer questions call for different retrieval mechanisms.

  -----------------------------------------------------------------------
  Developer question                  Best retrieval mechanism
  ----------------------------------- -----------------------------------
  What is a facility?                 Semantic search

  Find `CalculateFacilityBalance`     Exact identifier search

  Which procedures call this          Relationship lookup
  procedure?                          

  Where is facility maintenance       Hybrid search
  implemented?                        

  How does the legacy implementation  Cross-repository retrieval
  compare with the new service?       

  Why did we choose separate snapshot Architecture decision retrieval
  databases?                          
  -----------------------------------------------------------------------

Build a retrieval abstraction rather than coupling the application
directly to a vector database.

# 3. Language choice: Python or .NET?

**Recommendation: Python for the knowledge/AI backend, and .NET only
where it provides a clear integration advantage.**

Python is not inherently better for building backend services, but its
ecosystem for experimenting with document processing, code parsing,
embeddings, retrieval, and LLM workflows is more mature.

A suggested division of responsibilities:

  Responsibility                        Recommended technology
  ------------------------------------- --------------------------------------
  Git repository processing             Python
  File discovery and parsing            Python + Tree-sitter
  SQL parsing                           Python + appropriate T-SQL parser
  ASP parsing                           Python + custom extraction initially
  Document processing (PDF, Markdown)   Python
  LLM integration                       Python
  Embeddings and indexing               Python
  RAG orchestration                     Python
  Backend API                           Python FastAPI
  Chat UI (eventually)                  React
  Integration with Claude Code          MCP server

The entire system could be built in Python. There is no reason to
introduce a .NET service simply because the product itself is written in
.NET.

## 3.1 What about Microsoft Semantic Kernel?

Semantic Kernel is worth knowing about, particularly in a Microsoft/.NET
ecosystem. It provides abstractions for vector stores, search, and AI
orchestration.

However, do not choose it solely to keep the technology consistent with
the day job.

Preferred direction:

-   Python for ingestion and retrieval.
-   LlamaIndex for selected RAG capabilities.
-   FastAPI for the service interface.
-   React if/when a UI is needed.
-   MCP for integration with Claude Code.

Keep business logic and data contracts independent of LlamaIndex.
Replacing it with Haystack or a custom implementation should remain
possible.

# 4. The architecture

Start with a **modular monolith**, not microservices.

The existing product modernization already involves decomposing a
monolith. There is no need to build another distributed system to solve
this problem.

## 4.1 Logical architecture

``` text
                         KNOWLEDGE SOURCES
       +----------------+----------------+----------------+
       |                |                |                |
  Legacy Git       Modern Git       Documentation    Domain knowledge
  ASP, SQL         C#, React, Helm  Markdown, PDFs   CLO concepts,
                                                     indentures
       |                |                |                |
       +----------------+----------------+----------------+
                                |
                                v
                       KNOWLEDGE INGESTION
              File discovery | Parsing | Chunking
              Metadata extraction | LLM enrichment
                                |
                                v
                         KNOWLEDGE STORAGE
       +----------------+----------------+----------------+
       |                |                |                |
   Vector index    Full-text index   Metadata store   Relationships
  Semantic search  Exact matches    Source/version    Calls, refs,
                                                   dependencies
       +----------------+----------------+----------------+
                                |
                                v
                      KNOWLEDGE / RETRIEVAL API
          Search | Retrieve | Expand relationships
                    Grounded answer generation
                                |
                                v
                             CONSUMERS
                       +------------------+
                       |                  |
                    Chat UI          Claude Code
                                      via MCP
```

There are two important design principles.

### Separate ingestion from question answering

Ingestion runs when repositories change or documents are added. Query
processing runs whenever a developer asks something.

Do not parse the repository every time someone asks a question.

### Make storage replaceable

Do not make LlamaIndex objects the permanent data model. Store your own
document IDs, chunk IDs, source metadata, and relationships.

## 4.2 Storage choices

Start with **PostgreSQL + pgvector**.

This gives you:

-   Normal relational tables for documents, chunks, symbols, and
    relationships.
-   Vector embeddings for semantic search.
-   PostgreSQL full-text search for keyword retrieval.
-   Transactions and referential integrity.
-   One database to operate and maintain.

Qdrant is also a reasonable alternative, particularly if vector
retrieval eventually needs to scale independently.

Do not introduce PostgreSQL and Qdrant simultaneously.

An initial schema might look like this:

``` text
Repositories
    Id
    Name
    Url
    Branch
    CurrentCommit

Sources
    Id
    RepositoryId
    FilePath
    FileHash
    Language
    LastIndexedCommit

Chunks
    Id
    SourceId
    SymbolName
    SymbolType
    Content
    StartLine
    EndLine
    Embedding

Relationships
    Id
    SourceChunkId
    TargetChunkId
    RelationshipType

Documents
    Id
    SourceType
    Title
    FilePath
    Version

IngestionRuns
    Id
    RepositoryId
    Commit
    StartedAt
    CompletedAt
    Status
```

This is illustrative, not a final schema. For example, a separate
`Symbols` table may eventually be useful so that multiple chunks can
belong to one symbol.

Do not store only the latest repository version. At a minimum, preserve
the commit SHA associated with indexed content. This matters when a
developer asks about code that existed before a migration.

## 4.3 How to use LlamaIndex

Use LlamaIndex for the parts where it adds value:

-   Embedding generation.
-   Ingestion transformations.
-   Vector store integration.
-   Retrieval abstractions.
-   Query processing.

Its ingestion pipeline supports transformation caching and document
hash-based change detection, which can help with incremental indexing.

Implement these independently:

-   Git synchronization.
-   Source code parsing.
-   SQL dependency extraction.
-   ASP-specific parsing.
-   Semantic chunk construction.
-   Repository relationship extraction.

These are product-specific engineering components and should not be
hidden inside a framework.

# 6. How developers will use it

Support two interfaces eventually, but do not build both immediately.

## 6.1 Chat interface

Eventually, a simple internal web application could provide a
conversation interface.

Example developer question:

> How does the legacy application calculate the facility principal
> balance, and where is this implemented?

An illustrative response might say:

> The legacy implementation appears to calculate facility principal
> balance through the following components:
>
> 1.  `CalculateFacilityBalance` --- SQL stored procedure handling the
>     calculation.
> 2.  `FacilityTransaction` --- source of transaction-related data.
> 3.  `FacilityDetails.asp` --- legacy page invoking the calculation.
>
> The calculation appears to account for transaction adjustments. I
> would need to inspect the relevant branches and related procedures
> before confirming all business scenarios.

It should cite exact Git files and line numbers.

**Source citations are critical.** Developers must be able to click
through to the actual Git file and line numbers. Otherwise, they have no
way to distinguish a correct explanation from an AI hallucination.

## 6.2 Claude Code integration

This is potentially where the project could deliver significant value.

Rather than developing another coding assistant, give Claude access to
product knowledge.

Use **Model Context Protocol (MCP)**.

MCP is a standardized interface through which an AI assistant can invoke
tools exposed by another application.

The knowledge system could expose tools such as:

  -----------------------------------------------------------------------
  MCP tool                            Purpose
  ----------------------------------- -----------------------------------
  `search_product_knowledge`          Search CLO domain knowledge

  `search_legacy_code`                Find relevant legacy implementation

  `search_modern_code`                Find modernized implementation

  `get_symbol_details`                Retrieve a complete
                                      procedure/function

  `get_dependencies`                  Find callers, callees, and related
                                      tables

  `compare_implementations`           Compare legacy and modern
                                      implementations

  `explain_concept`                   Explain a CLO concept with
                                      supporting sources
  -----------------------------------------------------------------------

Claude Code can connect to MCP servers, including project-level
configurations.

Imagine a developer working on the facility service:

``` text
I need to implement facility maintenance
in the modern portfolio service.

Before writing code, help me understand:

1. What is a facility in our product?
2. What are its relationships?
3. Where is it maintained in the legacy app?
4. What business rules apply?
5. What existing modern services should I
   consider when designing this?
```

Claude Code can call the MCP tools, retrieve relevant context, and
reason about the implementation.

The distinction is:

-   Your knowledge system supplies product-specific context.
-   Claude Code supplies the coding capabilities.

There is no need to build code generation, code editing, or agent
orchestration into the knowledge system initially.

Start with read-only knowledge tools. Let Claude generate code and
propose changes, but do not give the knowledge service permission to
modify repositories, databases, or deployments.

# 7. Deployment model

Keep deployment simple initially.

The organization already has Kubernetes, Helm, PostgreSQL,
observability, and container infrastructure. Those capabilities can be
reused eventually, but Kubernetes should not be a prerequisite for the
first working version.

## Phase 1: Local development

Run everything locally:

-   Python application: ingestion, retrieval, and API.
-   PostgreSQL in Docker: pgvector and metadata.
-   Local Git checkouts: legacy and modern repositories.
-   Approved LLM/embedding provider: accessed through the
    corporate-approved endpoint.

Start with:

-   Python virtual environment.
-   PostgreSQL in Docker.
-   A CLI for ingestion.
-   A CLI for asking questions.
-   An approved LLM API.

No UI, Kubernetes, or MCP initially.

## Phase 2: Internal deployment

Once quality is established:

-   Containerize the Python application.
-   Deploy PostgreSQL using the organization's existing infrastructure.
-   Run ingestion as a scheduled Kubernetes Job or CI/CD-triggered job.
-   Deploy the query API as a containerized service.
-   Add internal authentication and authorization.
-   Expose it through an internal gateway.

Initially, two workloads should be sufficient:

  Workload           Responsibility
  ------------------ ----------------------------------------
  Ingestion worker   Git synchronization, parsing, indexing
  Knowledge API      Search, retrieval, and answering

The ingestion worker can run on demand or periodically. The API remains
available to developers.

## Phase 3: Developer-facing interfaces

Add:

-   React chatbot, if useful.
-   MCP server for Claude Code.
-   Authentication using existing Keycloak infrastructure.
-   Repository and source-level access controls.

Access control must be enforced during retrieval, not just at the UI. If
developers have different permissions across repositories, the knowledge
system must preserve those restrictions.

## 7.1 Enterprise data security

Before selecting an embedding or LLM provider, establish:

1.  Are source files permitted to leave the corporate network?
2.  Can code be sent to an externally hosted embedding service?
3.  Can code snippets be sent to an externally hosted LLM?
4.  What are the retention and training policies?
5.  Do different repositories or teams require different access
    controls?

Embeddings are derived from source code; they should not be treated as
harmless or public metadata.

Put provider access behind interfaces so you can switch between an
approved hosted model and an internally hosted model without redesigning
the ingestion pipeline.

# 8. Incremental implementation roadmap

Resist the temptation to build the entire architecture upfront.

Define small milestones with tangible outputs. At each milestone,
evaluate the results before adding complexity.

## Milestone 1 --- Basic codebase ingestion

-   Read one Git repository.
-   Identify `.sql` and `.asp` files.
-   Extract procedures, functions, and other logical blocks.
-   Store the extracted content and metadata.
-   Build a simple CLI to inspect chunks.

**Deliverable:** A collection of structured code chunks suitable for
search, even before implementing RAG.

## Milestone 2 --- Basic RAG

-   Generate embeddings.
-   Store them in pgvector.
-   Implement semantic search.
-   Pass retrieved chunks to an LLM.
-   Return answers with file and line references.

**Deliverable:** Ask questions about the legacy codebase and get
grounded answers.

## Milestone 3 --- Better retrieval

-   Add PostgreSQL full-text search.
-   Combine keyword and semantic results.
-   Improve ranking.
-   Retrieve complete procedures when a smaller chunk matches.

**Deliverable:** More reliable retrieval of both conceptual and exact
code references.

## Milestone 4 --- Product knowledge

-   Ingest Markdown documents.
-   Ingest PDFs, including relevant indentures.
-   Extract domain terminology and definitions.
-   Add source-type and document-version metadata.

**Deliverable:** Answers combining product concepts and implementation.

## Milestone 5 --- Relationships and enrichment

-   Extract procedure calls and table dependencies.
-   Map ASP pages to stored procedures.
-   Generate LLM-assisted explanations of important procedures.
-   Store candidate relationships with supporting evidence.

**Deliverable:** Understand how functionality flows through the legacy
application.

## Milestone 6 --- Modern codebase

-   Ingest modern .NET services.
-   Understand gRPC contracts and service boundaries.
-   Map legacy functionality to modern implementations.
-   Ingest architecture decisions and design documents.

**Deliverable:** Cross-generation product knowledge.

## Milestone 7 --- Claude Code integration

-   Implement MCP tools.
-   Connect Claude Code.
-   Expose search, explanation, and dependency lookup.
-   Test real development workflows.

**Deliverable:** Product-aware coding assistance.

## Milestone 8 --- Engineering assistant

-   Architecture recommendations.
-   Design reviews.
-   Legacy-to-modern migration proposals.
-   Code reviews against product rules.
-   Eventually, multi-step agent workflows.

**Deliverable:** A more capable engineering assistant.

Notice that the first milestone does not even require an LLM. Do that
deliberately.

If you cannot extract meaningful chunks from the source code, adding
embeddings and an LLM will not fix the underlying problem.

## 8.1 Evaluate each milestone

Do not judge the project by whether the chatbot gives impressive
answers.

Build a small evaluation dataset with questions whose answers are
already known.

  -----------------------------------------------------------------------
  Question                            What you're testing
  ----------------------------------- -----------------------------------
  Where is facility maintenance       Code discovery
  implemented?                        

  What does procedure X do?           Structural and semantic
                                      understanding

  Which tables does procedure X       Dependency extraction
  modify?                             

  What is an IC test?                 Domain knowledge

  Where is the IC test calculated?    Domain-to-code mapping

  What calls procedure X?             Relationship retrieval

  How does legacy functionality map   Cross-repository retrieval
  to the new service?                 
  -----------------------------------------------------------------------

For every question, record:

-   Expected source files.
-   Expected procedures/functions.
-   Important business concepts.
-   Whether the answer should be definitive or qualified.

Then evaluate:

1.  Did retrieval find the correct sources?
2.  Did the LLM interpret them correctly?
3.  Did the answer cite the right locations?
4.  Did it invent any business rules?
5.  Could a developer actually use the answer?

This avoids building something that sounds knowledgeable but is not
useful.

  Pitfall                             What to do instead

  Building an autonomous agent        Start with deterministic retrieval
  immediately                         and grounded answers

  indiscriminately                    irrelevant assets, and duplicates

  Using generic fixed-size chunks     Use procedure/function/page
                                      boundaries

                                      distinguish generated
                                      interpretations

  Building a graph database upfront   Store relationships in PostgreSQL

  validating retrieval                search results

  implementations without labels      implementation generation

  write access                        controlled actions much later
  -----------------------------------------------------------------------

## 9.1 Business rule ambiguity

This is particularly important in your application.

Suppose an LLM finds two procedures that calculate the same compliance
metric but handle different scenarios.

It must not confidently merge their explanations into one generalized
rule.

Eventually, the system should understand:

-   Which rules apply to which CLO structures.
-   Which scenarios trigger special handling.
-   Which behavior is contractual versus product-specific.
-   Which behavior is legacy implementation detail.
-   Which behavior is the intended modern design.

This is where domain documentation and human-reviewed explanations
become extremely valuable.

# 12. Where to start

Narrow the first iteration considerably.

Do not start with the entire legacy repository, all documentation,
modern repositories, and an LLM.

Start with a representative subset of the legacy codebase.

Choose:

-   20--30 stored procedures related to one reasonably self-contained
    business capability.
-   A few classic ASP pages that invoke those procedures.
-   The relevant table definitions.
-   Any existing documentation for that capability.

Perhaps facility management, if the code is reasonably self-contained.

Build a small ingestion utility that:

1.  Reads those files.
2.  Extracts procedures and ASP functions/subroutines.
3.  Preserves the original source and line numbers.
4.  Produces structured JSON representations of the extracted chunks.
5.  Allows you to inspect the output.

Then review the output with someone who understands that part of the
product.

Ask them:

-   Are these logical boundaries?
-   Is important business logic getting separated from its context?
-   Are SQL statements embedded in ASP being captured?
-   Are comments and special-case conditions preserved?
-   Is there enough information to understand what each procedure does?

Only when satisfied with that foundation should you introduce
embeddings.

This is a much better way to validate foundational assumptions before
committing to the RAG architecture.

# 13. The long-term framing

The ultimate goal is not necessarily to build a CLO-specific LLM. There
is no need to train a model from scratch.

The goal is a general-purpose LLM equipped with:

-   Your product's knowledge.
-   Access to the actual implementation.
-   An understanding of your architecture.
-   The ability to retrieve supporting evidence.
-   Tools to inspect and reason about the codebase.

Eventually, it should also be able to use those capabilities during
development.

Describe the end goal as a:

**CLO Product Knowledge Platform with an AI Engineering Assistant on
top.**

That framing is useful because the knowledge platform remains valuable
even if you change LLM providers, replace Claude Code, or switch RAG
frameworks.

The existing modernization effort provides a particularly good use case:
you have both the legacy implementation and the emerging architecture,
so the system can help developers understand not just what the product
does, but how to migrate it responsibly.
