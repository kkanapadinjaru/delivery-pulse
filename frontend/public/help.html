Work Item Metrics

Total Work Items Volume

Count of work items (of the configured types) that were ever assigned to the developer and had activity (state or assignment changes) within the selected date range. Uses the WIQL EVER operator so items are counted even if the developer is no longer the current assignee.

Completed Quality

Count of work items where the developer handed off the item to someone else (typically back to QA or a reviewer). This is determined by looking at the first time the AssignedTo field changed FROM the developer TO another person in the work item history. An item is considered "completed" from the developer's perspective at the point of first reassignment.

Avg Days to Complete Quality

Average calendar days from when the developer was first assigned a work item to when they first reassigned it away. Only the first assignment cycle is counted — if an item bounces back and forth, subsequent cycles don't inflate this number. Only items that have both an assignment and reassignment date contribute to this average.

Bounced Back Quality

Count of work items that were reassigned back to the developer after they had already handed them off. This indicates the reviewer or tester determined the work was incomplete or incorrect and sent it back. A higher bounce-back count suggests quality issues in the initial delivery.

This is NOT based on work item state changes (e.g., Resolved to Active). It specifically tracks assignment changes where the developer receives the item again after previously giving it away.

Reopen Rate Thresholds Quality

The reopen rate is the percentage of work items that bounced back out of total items worked. The quality badge uses these thresholds:

RatingThresholdMeaning
Excellent0%No items bounced back at all
Good1–10%Low bounce-back rate, acceptable quality
Needs Improvement11–25%Moderate rate, work may be incomplete
Concerning> 25%High rate, significant quality issues

Priority 1 / Priority 2 Volume

Breakdown of work items by priority level, where priority is set on the item.

Pull Request Metrics

PRs Merged Volume

Total pull requests created by the developer in the selected date range that were successfully completed (merged into target branch). Includes PRs across all repositories in the project.

Total Commits Volume

Sum of all commits across all PRs raised by the developer in the date range. This represents the total code change volume.

Avg PR Cycle (days) Quality

Average calendar days from PR creation to PR completion (merge). Only completed PRs contribute to this metric. A shorter cycle indicates faster code review turnaround. Very short cycles (under a few hours) may indicate PRs merged without thorough review.

Files Changed Volume

Total number of files modified across all merged PRs. Calculated from the final iteration of each PR (representing the net diff against the target branch). Gives a sense of the breadth of code changes.

Actionable Comments Quality

Count of reviewer comments on PRs that were followed by subsequent code pushes. The logic:

1. A comment thread is initiated by someone other than the PR author (reviewer feedback).
2. The comment was left on an iteration (push) that is NOT the final iteration — meaning new code was pushed after the comment.
3. This indicates the developer had to make code changes to address the feedback.

A higher count suggests more reviewer feedback required code changes, which may indicate either thorough reviews or code that needed more revision before merge.

Rework PRs Quality

Identifies work items that have multiple pull requests to the same repository. This is a quality signal — it often means the initial PR didn't fully address the requirement, or the fix needed follow-up corrections in the same codebase.

A work item having PRs across different repositories is expected (e.g., frontend + backend changes) and is not flagged. Only same-repo duplicates are counted as potential rework.

Details Grid

The collapsible details section shows individual work items with their linked PRs. The "Linked PR" column maps PRs to work items using Azure DevOps' built-in PR-to-work-item linking (typically done via commit messages referencing #WorkItemID or manual linking in the PR).

PRs that aren't linked to any work item in the current result set are shown in a separate "Unlinked PRs" sub-table.

Note on data sources: Work items are queried using WIQL with the EVER operator on AssignedTo, which finds items regardless of current assignee. The work item types included are configurable via Settings. PR data comes from the Azure DevOps Git API filtered by creator identity and date range. The correlation between PRs and work items depends on teams properly linking PRs to work items in Azure DevOps.

How This Helps Assess Delivery Quality

Developer throughput: Total Work Items + PRs Merged give a volume picture of how much work the developer is processing.

Completion quality: Bounced Back count and Actionable Comments indicate whether work is complete on the first attempt or requires rework.

Responsiveness: Avg Days to Complete shows how quickly items are addressed once assigned. Avg PR Cycle shows how fast code moves from review to merge.

Code review engagement: Actionable Comments shows how much reviewer feedback translates to actual code changes, indicating review effectiveness.
