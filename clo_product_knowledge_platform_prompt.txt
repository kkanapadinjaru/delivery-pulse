As for the asset management product, we originally decided to break up the monolith into several smaller gRPC dotnet services
- domaindata  - all the application setup and common shared data required for the compliance and portfolio features (think of calendars, user defined data, lookups, ratings, index history etc.)
- compliance modeling - all the compliance rules setup
- compliance snapshots - the service that creates snapshot of portfolio data and runs the rules.
- portfolio services - We have not fully designed these yet - but thinking of 3 separate parts - transactions, instrument setup, organizations setup

The original idea of splitting to the services was borne out of performance and maintenance. In the legacy app, since all the data reside in the same database, when a compliance engine (a bunch of stored procedures in sql server runs), it's a huge amount of compute on large sets of data and makes the rest of the app unusable since the db server is fully used up. The idea of creating smaller gRPC services means each service can own its database, and serve up the data which then makes it a deployment decision on what servers the individual databases go to. We can configure such that the snapshots service gets a database provisioned in a different database server, portfolio transactions can be its own and the rest of the services can all be in 1 place etc. But this also adds another challenge - how do we transport all these data into the snapshots database when we ceate a snapshot object (point in time snapshot of all the portfolio and modeling information required by engine).
So, nothing is set in stone here.

The important part: code-aware parsing
design the ingestion process independently of the RAG framework.
For example:
Git repository
Checkout / branch / commit
File discovery and filtering
.asp · .aspx · .cs · .sql · .config
Language-specific parsers
AST / syntax tree / symbol extraction
Semantic chunking
Functions · procedures · classes · SQL blocks
LlamaIndex ingestion pipeline
Metadata · embeddings · caching
Vector + keyword index
Hybrid retrieval
For parsing, consider:
- Tree-sitter: A good starting point for syntax-aware parsing across multiple languages.
- Microsoft Roslyn: If you also have C# and ASP.NET code. It provides much richer C# semantic information than generic text splitting.
- SQLGlot: Useful for parsing SQL and extracting SQL structure. Check its T-SQL dialect support against your actual SQL Server syntax.
- ANTLR: Worth considering if you need custom grammar support, particularly for legacy ASP/VBScript.
One caveat: classic ASP (.asp with VBScript/JScript embedded in HTML) is different from ASP.NET (.aspx). You shouldn't assume a C# parser or generic HTML parser will correctly understand classic ASP.
3. chunk the code - invest most of the engineering effort.
Avoid fixed-size chunks such as 500 tokens with 50-token overlap. Instead, use semantic boundaries.
For SQL:
- One stored procedure per logical chunk.
- Individual functions.
- Views and triggers.
- Table definitions where useful.
- Preserve comments and relevant SQL dependencies.
For ASP / ASP.NET:
- Individual functions and subroutines.
- Page lifecycle handlers.
- Event handlers.
- Business logic blocks.
- SQL queries embedded in the pages.
For every chunk, I'd attach metadata:
{
  "repository": "PortfolioManager",
  "branch": "main",
  "commit": "abc123",
  "file": "Database/Compliance.sql",
  "language": "sql",
  "symbol": "CalculateCompliance",
  "symbol_type": "stored_procedure",
  "start_line": 120,
  "end_line": 245
}
preserve relationships:
- Which procedures call other procedures?
- Which tables does a procedure read or modify?
- Which ASP page invokes a particular stored procedure?
- Which functions are referenced by other functions?
This eventually allows you to build something more useful than simple vector search: a lightweight code knowledge graph.
4. Retrieval: don't use vector search alone
For source code, I'd combine:
1. Vector search: Find conceptually related code.
2. Keyword/BM25 search: Find exact identifiers, table names, procedure names and variables.
3. Relationship expansion: Retrieve callers, callees and related SQL objects.
4. Reranking: Improve the relevance of retrieved chunks.
For example, someone might ask:
"Where is the calculation of the portfolio's weighted average spread performed?"
Vector search can find conceptually related logic, but keyword search might find the actual column names or stored procedures. Relationship expansion can then identify the calling ASP page.
That combination is considerably more useful than pure vector RAG.
5. My recommended technology stack

Ingestion orchestration - Python
RAG framework - LlamaIndex
Code parsing - Tree-sitter
C# parsing (if applicable) - Roslyn
SQL parsing - SQLGlot / T-SQL parser
Embeddings - Your chosen embedding model (Huggingface or similar)
Vector database -Qdrant or PostgreSQL + pgvector
Keyword search - PostgreSQL full-text or Elasticsearch

Keep the parser and chunking implementation independent of LlamaIndex. Tlexibility to switch frameworks without rewriting code understanding layer.
6. One additional consideration: incremental indexing
Since the source is in Git, use Git as the source of truth.
You don't want to reprocess the entire repository whenever someone pushes a change.
Track:
- Commit SHA
- File hash
- Chunk ID
- Symbol name
- Parser version
- Embedding model/version
On a new commit:
- Identify changed files.
- Reparse those files.
- Replace their old chunks.
- Remove chunks belonging to deleted files.
- Leave unchanged files alone.
LlamaIndex's ingestion pipeline has caching and document tracking mechanisms that can help here. 
LlamaIndex Python Documentation+1

Final recommendation
My pick
 LlamaIndex + Tree-sitter + custom semantic chunking.
